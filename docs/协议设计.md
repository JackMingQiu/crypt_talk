# CryptoTalk 协议设计文档

- 文档版本：1.0
- 对应程序版本：1.0.0（协议前缀 `CTK1:`，信封版本 `v=1`）
- 密码库：BouncyCastle `bcprov-jdk18on 1.86`（轻量级 API，不依赖 JCA Provider）
- 适用平台：macOS（JVM Desktop）/ Android（API 26+）
- 文档依据：`composeApp/src/sharedMain/kotlin/com/crypttalk/` 下的实际实现

---

## 1. 总览

### 1.1 系统组成

CryptoTalk 是纯本地程序，不含服务器。双方通过任意第三方通道（微信、邮件等）互相复制粘贴字符串完成通信。第三方通道中传输的只有 `CTK1:` 开头的密文信封，明文只在各自设备的进程内出现。

```
┌────────────── 设备 A ──────────────┐        ┌────────────── 设备 B ──────────────┐
│ AppController                      │        │ AppController                      │
│  ├─ 身份密钥 (sk_A, pk_A)          │        │  ├─ 身份密钥 (sk_B, pk_B)          │
│  ├─ 本地存储 profile/contacts/...  │        │  ├─ 本地存储 profile/contacts/...  │
│  └─ UI（Compose Multiplatform）    │        │  └─ UI（Compose Multiplatform）    │
└──────────┬─────────────────────────┘        └──────────┬─────────────────────────┘
           │  用户复制 CTK1:...（密文）                            │
           └──────────────► 第三方通道（明文可见） ◄──────────────┘
```

### 1.2 信任模型

- 身份长期密钥 `(sk, pk)` 首次由本地生成，`pk` 通过带外方式（人工核对/外部网络）交给对方，作为**首次信任锚点**。
- 之后每次会话都使用临时密钥 `(eph_sk, eph_pk)`，并用身份私钥对临时公钥签名，把「本次会话的临时公钥」绑定到「已信任的长期身份」上。
- 消息只由一次性会话密钥加密；会话结束即废弃该密钥（历史密文仍可用本地保存的会话密钥解密，见 §11、§14）。

### 1.3 协议清单

| 编号 | 协议 | 主要算法 | 参与接口 |
|---|---|---|---|
| P1 | 身份初始化 + PIN 加密私钥 | SM2 密钥生成、SM3、SM4-GCM | `Sm2.generateKeyPair`、`PinCipher.deriveEncKey`、`PinCipher.encrypt` |
| P2 | 解锁（PIN 认证） | SM3、SM4-GCM、SM2 公钥推导 | `PinCipher.decrypt`、`Sm2.privateKeyFromBytes`、`Sm2.derivePublicKey` |
| P3 | 联系人 / 首次信任 | SM2 公钥解码与规范化、SM3 指纹 | `Sm2.decodePublicKey`、`Protocol.fingerprint` |
| P4 | 会话建立握手（邀请 / 接受） | SM2 密钥生成与签名、SM2-ECDH、SM3 | `Protocol.createInvite`、`parseInvite`、`createAccept`、`parseAccept`、`deriveInitiatorSession` |
| P5 | 消息加密与解密 | SM4-GCM、SM3（AAD 绑定） | `Protocol.encryptMessage`、`decryptMessage` |
| P6 | 密码信封编码 | URL-safe Base64、JSON | `Protocol.encode`、`Protocol.decode` |
| P7 | 本地加密存储 | SM4-GCM + 三类 AAD | `PinCipher.encrypt/decrypt`、`Store` |

## 2. 通用约定

| 项目 | 约定 |
|---|---|
| 字符编码 | 所有字符串进入密码运算前统一转 UTF-8 |
| 十六进制 | 小写、无分隔、无 `0x` 前缀；解码时容忍空白字符，输出统一小写 |
| Base64 | URL-safe 字母表（`-`、`_`），**不带 `=` 填充** |
| 随机数 | `java.security.SecureRandom`（密钥、nonce 均来自它） |
| 时间 | Unix 时间戳，单位**秒**（`System.currentTimeMillis()/1000`） |
| 公钥编码 | SM2 **未压缩点**：`04 || X(32B) || Y(32B)`，共 65 字节 |
| 私钥编码 | 32 字节大端整数 |
| 签名编码 | ASN.1 DER 的 `SEQUENCE { r INTEGER, s INTEGER }`（BouncyCastle 默认），约 70–72 字节 |
| 长度校验 | 私钥 `1 ≤ d < n`；公钥必须能解码、非无穷远点、在 SM2 曲线上（见 `Sm2.decodePublicKey`） |

## 3. 底层算法与接口

### 3.1 SM2（GB/T 32918）

**曲线参数**：`sm2p256v1`（`GMNamedCurves.getByName("sm2p256v1")`），基点 `G`，阶 `n`，余因子 `h=1`，256 位素域。

**用途**：仅使用「密钥生成」「数字签名/验签」「ECDH 密钥协商」三种运算；**不使用 SM2 公钥加密**（消息加密由 SM4-GCM 完成）。

| 运算 | 实现 | 说明 |
|---|---|---|
| 密钥生成 | `ECKeyPairGenerator` + `ECKeyGenerationParameters` | 生成 `d ∈ [1, n-1]`，`Q = d·G` |
| 签名 | `SM2Signer`（`init(true, ECPrivateKeyParameters)`） | 默认用户标识 `1234567812345678`（ASCII，BC 内置），摘要 `e = SM3(Z_A ‖ M)` |
| 验签 | `SM2Signer`（`init(false, ECPublicKeyParameters)`） | DER 签名；任何异常一律返回 `false` |
| ECDH | `peerPk.multiply(d).normalize()` | 取共享点 **X 坐标**，定长 32 字节（`toFixed32`） |

接口（`crypto/Sm2.kt`）：

```kotlin
object Sm2 {
    data class KeyPair(val d: BigInteger, val q: ECPoint)

    fun generateKeyPair(): KeyPair
    fun derivePublicKey(d: BigInteger): ECPoint
    fun publicKeyBytes(q: ECPoint): ByteArray              // 65 字节未压缩
    fun decodePublicKey(bytes: ByteArray): ECPoint         // 校验格式/曲线
    fun sign(privateKey: BigInteger, message: ByteArray): ByteArray   // DER
    fun verify(publicKey: ECPoint, message: ByteArray, signature: ByteArray): Boolean
    fun ecdh(privateKey: BigInteger, peerPublicKey: ECPoint): ByteArray // 32 字节 X
    fun privateKeyBytes(d: BigInteger): ByteArray          // 32 字节
    fun privateKeyFromBytes(bytes: ByteArray): BigInteger  // 校验 1 ≤ d < n
    fun toPublicKeyHex(bytes: ByteArray): String           // 规范化
}
```

> 注意：签名只覆盖传入的 `message` 字节。本项目 P4 中该消息就是 65 字节临时公钥，**不含**协议类型、会话 ID、用户名等上下文（见 §14 限制）。

### 3.2 SM3（GB/T 32905）

输出 32 字节摘要。支持多段输入按顺序拼接后哈希：

```kotlin
object Sm3 {
    fun hash(vararg parts: ByteArray): ByteArray   // 32 字节
}
```

实现：`org.bouncycastle.crypto.digests.SM3Digest`。本项目不另行添加长度前缀或分隔符，拼接顺序即协议定义顺序。

### 3.3 SM4（GB/T 32907）+ GCM

所有对称加密均使用 **SM4-GCM**（认证加密），参数固定：

| 参数 | 值 |
|---|---|
| 密钥长度 | 128 位（16 字节） |
| Nonce | 96 位（12 字节），每次加密由 `SecureRandom` 新生成 |
| 认证标签 | 128 位（16 字节） |
| AAD | 由各协议指定，UTF-8 字节串 |
| 密文布局 | `ciphertext ‖ tag`（BC `GCMBlockCipher` 输出） |
| 存储/传输布局 | `nonce(12B) ‖ ciphertext ‖ tag(16B)`，整体再做 Base64（非信封场景） |

```kotlin
object Sm4 {
    const val KEY_SIZE = 16
    const val NONCE_SIZE = 12
    const val TAG_BITS = 128

    fun gcmEncrypt(key: ByteArray, nonce: ByteArray, plaintext: ByteArray, aad: ByteArray): ByteArray
    fun gcmDecrypt(key: ByteArray, nonce: ByteArray, ciphertext: ByteArray, aad: ByteArray): ByteArray
}
```

解密失败（密钥错误、AAD 不符、数据被篡改、标签不匹配）统一抛出 `CryptoException("解密失败：密钥错误或数据被篡改")`。

### 3.4 PIN 与本地加密接口（`crypto/PinCipher.kt`）

```kotlin
object PinCipher {
    const val PROFILE_SK_AAD  = "crypttalk/profile/sk/v1"
    const val SESSION_KEY_AAD = "crypttalk/session/key/v1"
    const val EPH_SK_AAD      = "crypttalk/session/eph-sk/v1"

    fun isValidPin(pin: String): Boolean                       // ^[!-~]{6,16}$
    fun deriveEncKey(pin: String, unix: Long): ByteArray       // 16 字节
    fun encrypt(encKey: ByteArray, plaintext: ByteArray, aad: String): String  // B64(nonce‖ct‖tag)
    fun decrypt(encKey: ByteArray, blob: String, aad: String): ByteArray
}
```

- PIN 合法字符：ASCII `0x21`–`0x7E`（数字、大小写字母、标点），**不含空格**，长度 6–16。
- `encrypt` 输出：URL-safe Base64 无填充，内容为 `nonce(12) ‖ ciphertext ‖ tag(16)`。
- `decrypt` 要求 Base64 解码后至少 28 字节，否则报「加密数据不完整」。

## 4. 密钥派生与标识

| 名称 | 公式 | 长度 | 实现 |
|---|---|---|---|
| `enc_k`（本地存储密钥） | `SM3(UTF8(pin) ‖ UTF8(decimal(unix)))[0..15]` | 16 B | `PinCipher.deriveEncKey` |
| ECDH 共享值 `sharedX` | `X(eph_sk_own · eph_pk_peer)` | 32 B | `Sm2.ecdh` |
| 会话密钥 `K` | `SM3(sharedX ‖ first ‖ second)[0..15]`，`first/second` 为两临时公钥按**无符号字典序**排序 | 16 B | `Protocol.deriveSessionKey` |
| 会话标识 `sid` | `Hex(SM3(eph_pk_initiator ‖ eph_pk_responder)[0..7])`，**顺序固定：发起方在前** | 16 个 hex 字符（8 B） | `Protocol.sessionId` |
| 公钥指纹 | `Hex(SM3(pk)[0..7])`，每 4 个字符一组显示（如 `a1b2 c3d4 e5f6 7890`） | 展示用 | `Protocol.fingerprint` |

说明：

- `unix` 是**创建身份时**的时间戳，随 `profile.json` 持久化，永久作为 `enc_k` 的输入之一；解锁时重新用「PIN + 存储的 unix」派生，因此改时间戳即无法解密。
- 排序保证两端独立计算得到同一会话密钥，且密钥与双方临时公钥绑定。
- 会话密钥与 `sid` 是两种不同派生：`sid` 有角色顺序，密钥排序无关。

## 5. 协议 P1：身份初始化与私钥加密

### 5.1 输入

- `username`：非空，去除首尾空白后 ≤ 32 字符
- `pin` / `confirmPin`：符合 §3.4 规则，且两次一致

### 5.2 流程

```
1. unix   ← 当前 Unix 秒
2. (d, Q) ← Sm2.generateKeyPair()                 // SM2 密钥生成
3. pk     ← Sm2.publicKeyBytes(Q)                 // 65B: 04‖X‖Y
4. enc_k  ← SM3(UTF8(pin) ‖ UTF8(decimal(unix)))[0..15]   // SM3 派生 128 位
5. sk     ← Sm2.privateKeyBytes(d)                // 32B 大端
6. skEnc  ← SM4-GCM_enc(enc_k, nonce, sk, AAD="crypttalk/profile/sk/v1")
            输出 Base64(nonce‖ct‖tag)
7. 持久化 Profile{version=1, username, pkHex=Hex(pk), skEnc, unix, createdAt=unix}
8. 内存置入 encKey=enc_k、identitySk=d、identityPk=pk，状态切换为「已解锁」
```

### 5.3 输出与存储

`profile.json`：

```json
{
  "version": 1,
  "username": "alice",
  "pkHex": "04....(130 hex chars)",
  "skEnc": "Base64URL(nonce‖ciphertext‖tag)",
  "unix": 1794211940,
  "createdAt": 1794211940
}
```

- 磁盘上**没有**明文私钥，只有 `skEnc`；`unix` 是解密材料的一部分，必须与 `skEnc` 一起保存。
- `pk` 可自由展示/复制（65 字节 → 130 个 hex 字符，以 `04` 开头）。

### 5.4 算法与接口对照

| 步骤 | 算法 | 接口 |
|---|---|---|
| 生成身份密钥 | SM2 密钥生成 | `Sm2.generateKeyPair()` |
| 公钥编码 | 未压缩点编码 | `Sm2.publicKeyBytes(q)` |
| PIN 派生 | SM3（单次） | `PinCipher.deriveEncKey(pin, unix)` |
| 私钥加密 | SM4-GCM（128 位 tag） | `PinCipher.encrypt(encK, sk, PROFILE_SK_AAD)` |
| 落盘 | JSON + 原子替换 | `Store.saveProfile` |

## 6. 协议 P2：解锁（PIN 认证）

### 6.1 流程

```
1. enc_k' ← SM3(UTF8(pin') ‖ UTF8(decimal(profile.unix)))[0..15]
2. sk'    ← SM4-GCM_dec(enc_k', profile.skEnc, AAD="crypttalk/profile/sk/v1")
3. d'     ← Sm2.privateKeyFromBytes(sk')     // 校验 1 ≤ d < n
4. Q'     ← Sm2.derivePublicKey(d')          // SM2 标量乘
5. 校验 Hex(Q') == profile.pkHex
   ├─ 不一致 → 返回 "PIN 错误"（不进入已解锁状态）
   └─ 一致   → 内存置入 enc_k/d/pk，加载联系人与历史，locked=false
6. 异常（GCM 标签失败/数据损坏）→ 统一提示 "PIN 错误"
```

### 6.2 认证原理

- **第一道**：SM4-GCM 的 128 位认证标签。错误 PIN 派生的 `enc_k'` 解密必然失败（除 2^-128 概率）。
- **第二道**：解密出的私钥重新推导公钥，与档案中的 `pkHex` 比对，防止档案被替换/部分损坏后以错误私钥进入。
- 应用启动时默认 `locked=true`；`lock()` 会清空 `enc_k`、`identitySk`、`identityPk`、会话密钥缓存与明文消息缓存。

### 6.3 接口

| 步骤 | 算法 | 接口 |
|---|---|---|
| 派生 | SM3 | `PinCipher.deriveEncKey` |
| 解密 | SM4-GCM | `PinCipher.decrypt` |
| 私钥校验 | 范围检查 | `Sm2.privateKeyFromBytes` |
| 公钥一致性 | SM2 标量乘 | `Sm2.derivePublicKey`、`Sm2.publicKeyBytes` |

## 7. 协议 P3：联系人 / 首次信任

### 7.1 新建聊天

界面输入「用户名」+「身份公钥（hex）」，确认后执行 `AppController.addContact`：

```
1. 名称去空白，非空且 ≤ 32 字符
2. bytes ← Hex.decode(pkInput)              // 容忍空白
3. point ← Sm2.decodePublicKey(bytes)       // 必须非无穷远、在曲线上
4. canonical ← Hex(Sm2.publicKeyBytes(point)) // 统一未压缩编码
5. 拒绝：canonical == 自己的 pkHex
6. 拒绝：与已有联系人公钥相同（忽略大小写）
7. Contact{id=UUID, name, pkHex=canonical, createdAt=now} 落盘
```

- 信任建立完全依赖用户通过外部可信渠道核对公钥本身；指纹 `Protocol.fingerprint(pk)` 用于人工比对。
- 联系人公钥在保存时已规范化，后续所有校验都做**规范字节比较**（`contentEquals`），避免同一曲线点不同编码绕过。

### 7.2 接口

| 操作 | 算法 | 接口 |
|---|---|---|
| 公钥校验/规范化 | SM2 点解码 | `Sm2.decodePublicKey`、`Sm2.publicKeyBytes` |
| 指纹 | SM3 | `Protocol.fingerprint` |
| 持久化 | JSON | `Store.saveContacts` |

## 8. 协议 P4：会话建立握手（邀请 / 接受）

握手目标：双方在**已互信身份公钥**的前提下，协商一个一次性 128 位会话密钥 `K`，并让双方都能确认对方确实持有对应身份私钥。

### 8.1 角色与临时密钥

| 角色 | 临时密钥 | 保存策略 |
|---|---|---|
| 发起方 A | `(eph_sk_A, eph_pk_A)` | 会话处于 `pending` 时，`eph_sk_A` 用 `enc_k` 加密存 `ephSkEnc`；收到接受码后立即清空 |
| 接受方 B | `(eph_sk_B, eph_pk_B)` | 生成后只用于计算，**不持久化私钥** |

### 8.2 步骤一：A 生成邀请码

```
1. (eph_sk_A, eph_pk_A) ← Sm2.generateKeyPair()
2. sig_A ← SM2Sign(sk_A, eph_pk_A)                  // 签名对象：65 字节临时公钥
3. 信封 invite:
     type="invite", from=username_A, pk=Hex(pk_A),
     eph=Hex(eph_pk_A), sig=B64(sig_A)
4. 本地新建 SessionRecord:
     sid="", role="initiator", status="pending",
     ephSkEnc=SM4GCM(enc_k, eph_sk_A, AAD="crypttalk/session/eph-sk/v1"),
     keyEnc="", peerEphPkHex="", outSeq=0, seenSeqs=[], lastCode=邀请码
   同一联系人原有的 active/pending 会话全部置为 ended
5. 输出邀请码（同时可复制）
```

### 8.3 步骤二：B 粘贴邀请码并生成接受码

```
1. 解析信封，要求 type="invite"，字段 pk/eph/sig 齐全
2. pk_A' ← Hex.decode(pk)；校验 SM2 公钥合法
3. 规范比较 pk_A' == 当前联系人 pkHex，否则 "邀请码不属于当前联系人"
4. 若信封 from 非空，要求 from == 联系人名称，否则拒绝
5. SM2Verify(pk_A', eph_pk_A, sig_A) 必须为 true，否则拒绝
6. (eph_sk_B, eph_pk_B) ← Sm2.generateKeyPair()
7. sig_B ← SM2Sign(sk_B, eph_pk_B)
8. sid    ← Hex(SM3(eph_pk_A ‖ eph_pk_B)[0..7])          // 发起方在前
9. sharedX ← ECDH(eph_sk_B, eph_pk_A)                    // SM2 点乘取 X
10. K      ← SM3(sharedX ‖ sort(eph_pk_A, eph_pk_B))[0..15]
11. 信封 accept:
      type="accept", from=username_B, pk=Hex(pk_B),
      eph=Hex(eph_pk_B), sig=B64(sig_B), sid=sid
12. 本地会话直接置 active:
      keyEnc=SM4GCM(enc_k, K, AAD="crypttalk/session/key/v1"),
      peerEphPkHex=Hex(eph_pk_A), ephSkEnc=""
    原有 active/pending 会话置 ended
13. 输出接受码，界面同时显示「会话已建立」
```

### 8.4 步骤三：A 粘贴接受码，完成握手

```
1. 解析要求 type="accept"，字段 pk/eph/sig/sid 齐全
2. 规范比较 pk_B' == 联系人 pkHex
3. SM2Verify(pk_B', eph_pk_B, sig_B) 必须为 true
4. 取当前 pending 会话，用 enc_k 解密 ephSkEnc 得 eph_sk_A
5. sid'    ← Hex(SM3(eph_pk_A ‖ eph_pk_B)[0..7])   // eph_pk_A 由 eph_sk_A 重新推导
6. 要求 sid' == 信封 sid，否则 "接受码与当前会话不匹配"
7. sharedX ← ECDH(eph_sk_A, eph_pk_B)
8. K       ← SM3(sharedX ‖ sort(eph_pk_A, eph_pk_B))[0..15]
9. 会话置 active：keyEnc=SM4GCM(enc_k, K, SESSION_KEY_AAD)，
   peerEphPkHex=Hex(eph_pk_B)，ephSkEnc 清空；K 放入内存缓存
```

### 8.5 握手时序

```
A                                          B
│ 生成 eph_A；sig_A=Sign(sk_A,eph_A)       │
│──── invite{from,pk_A,eph_A,sig_A} ─────►│ 验证 pk_A、sig_A
│                                          │ 生成 eph_B；sig_B=Sign(sk_B,eph_B)
│                                          │ sid=SM3(eph_A‖eph_B)[:8]
│                                          │ K=SM3(ECDH(ephB,ephA)‖sorted)[:16]
│◄─── accept{from,pk_B,eph_B,sig_B,sid} ──│
│ 验证 pk_B、sig_B、sid                     │
│ K=SM3(ECDH(ephA,ephB)‖sorted)[:16]       │
│ 会话 active                              │ 会话 active
```

### 8.6 算法与接口对照

| 步骤 | 算法 | 接口 |
|---|---|---|
| 临时密钥 | SM2 密钥生成 | `Sm2.generateKeyPair` |
| 身份认证 | SM2 签名 / 验签 | `Sm2.sign`、`Sm2.verify` |
| 公钥校验 | SM2 点解码 | `Sm2.decodePublicKey` |
| 密钥协商 | SM2-ECDH（X 坐标） | `Sm2.ecdh` |
| 密钥派生 | SM3 | `Protocol.deriveSessionKey` |
| 会话标识 | SM3 | `Protocol.sessionId` |
| 临时私钥保护 | SM4-GCM | `PinCipher.encrypt/decrypt`（`EPH_SK_AAD`） |
| 会话密钥保护 | SM4-GCM | `PinCipher.encrypt/decrypt`（`SESSION_KEY_AAD`） |

## 9. 协议 P5：消息加密与解密

### 9.1 发送

```
输入：明文 text（UTF-8）、当前 active 会话 (sid, K)、发送者 (from, pk)
1. seq   ← 该会话 outSeq + 1                  // 每个发送方独立计数，从 1 开始
2. nonce ← SecureRandom(12B)
3. AAD   ← UTF8("CTK1|msg|" + sid + "|" + from + "|" + Hex(pk) + "|" + seq)
4. ct    ← SM4-GCM_enc(K, nonce, UTF8(text), AAD)
5. 信封 msg: type="msg", from, pk=Hex(pk), sid, seq, nonce=B64, ct=B64
6. 输出 "CTK1:" + B64(JSON)，并复制到剪贴板
7. 本地保存密文信封（明文只缓存在内存），outSeq ← seq
```

### 9.2 接收

```
输入：信封、当前联系人
1. 要求 type="msg"，字段 sid/nonce/ct/from/pk/seq 齐全
2. 要求 Hex 比较 envelope.pk == 联系人 pkHex（忽略大小写）
3. 按 sid 查找该联系人最近一条会话记录
4. 取会话密钥 K：内存缓存 → 否则用 enc_k 解密 keyEnc
5. 若 seq ∈ seenSeqs → 拒绝 "这条消息已经解密过了"
6. 用信封中的 sid/from/pk/seq 重建 AAD
7. SM4-GCM_dec(K, nonce, ct, AAD)
   ├─ 失败 → 拒绝（不改动会话状态，不落盘）
   └─ 成功 → 保存密文信封与 seq，seenSeqs 追加 seq（只保留最近 500 条）
```

### 9.3 设计要点

- **完整性/认证**：AAD 把 `sid`、`from`、发送者公钥、`seq` 与密文绑定；任何字段被改动都会导致 GCM 校验失败。
- **来源绑定**：接收端先要求信封公钥等于已保存联系人公钥，再用**该会话专属密钥**解密，二者共同保证消息来自持有会话密钥的对方。
- **重放/重复**：按 `seq` 去重；同一密文再次粘贴会被拒绝。
- **乱序**：不强制顺序，只要 seq 未出现过即可接受（离线复制粘贴场景需要）。
- **明文不落盘**：`messages.json` 中 `text` 对普通消息为空串，只存密文信封；解锁后按需重新解密。

### 9.4 接口

| 步骤 | 算法 | 接口 |
|---|---|---|
| AAD 构造 | SM3 无关，UTF-8 字符串 | `Protocol.messageAad`（私有） |
| 加密 | SM4-GCM | `Protocol.encryptMessage` |
| 解密 | SM4-GCM | `Protocol.decryptMessage` |
| 会话密钥取用 | SM4-GCM + 缓存 | `AppController.sessionKey`（私有） |

## 10. 协议 P6：密码信封格式（`CTK1:`）

### 10.1 外层

```
CTK1:<Base64URL(UTF8(JSON))>
```

- 前缀固定 `CTK1:`；`decode` 会先删除所有空白，再在字符串中查找前缀位置，因此可容忍第三方聊天工具添加的说明文字/换行。
- 前缀之后只截取 `[A-Za-z0-9_-]` 连续的字符（遇到其他字符即停止）。
- Base64 为 URL-safe、无 `=` 填充。

### 10.2 内层 JSON（`Envelope`）

| 字段 | 类型 | 出现于 | 含义 |
|---|---|---|---|
| `v` | Int | 恒为 1，序列化时省略默认值 | 信封版本 |
| `type` | String | 全部 | `invite` / `accept` / `msg` |
| `from` | String? | 全部 | 发送者用户名（明文） |
| `pk` | String? | 全部 | 发送者身份公钥 hex（明文） |
| `eph` | String? | invite / accept | 临时公钥 hex（65B） |
| `sig` | String? | invite / accept | 对临时公钥的 SM2 DER 签名，Base64URL |
| `sid` | String? | accept / msg | 会话标识（16 hex 字符） |
| `seq` | Long? | msg | 发送方消息序号 |
| `nonce` | String? | msg | GCM nonce（12B），Base64URL |
| `ct` | String? | msg | 密文+标签，Base64URL |

序列化配置：`ignoreUnknownKeys=true`、`encodeDefaults=false`、`explicitNulls=false`（未使用字段不出现）。

### 10.3 示例（字段值为示意）

邀请码：

```json
{"type":"invite","from":"alice","pk":"04a1...","eph":"04b2...","sig":"MEUCIQ..."}
```

接受码：

```json
{"type":"accept","from":"bob","pk":"04c3...","eph":"04d4...","sig":"MEUCIQ...","sid":"9f3a1c02b7d84e65"}
```

消息：

```json
{"type":"msg","from":"alice","pk":"04a1...","sid":"9f3a1c02b7d84e65","seq":1,"nonce":"q83vAz...","ct":"k2Jd..."}
```

### 10.4 解析规则与错误

| 检查 | 失败提示 |
|---|---|
| 找不到 `CTK1:` 前缀 | 不是 CryptTalk 密文（应以 CTK1: 开头） |
| 前缀后为空 | 密文内容为空 |
| Base64/JSON 解析失败 | 密文格式无法解析 |
| 版本不为 1 | 不支持的协议版本：N |
| 类型未知 | 不支持的密文类型 |

接口：

```kotlin
object Protocol {
    fun encode(envelope: Envelope): String
    fun decode(text: String): Envelope
}
```

## 11. 协议 P7：本地存储格式

目录：

- macOS：`~/.crypt_talk/`
- Android：应用私有目录 `files/crypt_talk/`（`File(filesDir, "crypt_talk")`）

所有 JSON 采用 UTF-8、美化输出、`encodeDefaults=true`；写入采用「临时文件 + `ATOMIC_MOVE`（失败回退 `REPLACE_EXISTING`）」保证原子性。

### 11.1 `profile.json`

| 字段 | 类型 | 说明 |
|---|---|---|
| `version` | Int | 1 |
| `username` | String | 用户名 |
| `pkHex` | String | SM2 公钥（65B 未压缩） |
| `skEnc` | String | `B64(nonce‖SM4GCM(enc_k, sk, PROFILE_SK_AAD))` |
| `unix` | Long | 创建时间戳（秒），`enc_k` 派生材料 |
| `createdAt` | Long | 创建时间（秒） |

### 11.2 `contacts.json`

```json
{ "version": 1, "contacts": [ { "id": "UUID", "name": "bob", "pkHex": "04…", "createdAt": 1794211940 } ] }
```

### 11.3 `sessions.json`

```json
{
  "version": 1,
  "sessions": {
    "<contactId>": [
      {
        "sid": "9f3a1c02b7d84e65",
        "contactId": "…",
        "role": "initiator | responder",
        "peerEphPkHex": "04…",
        "keyEnc": "B64(nonce‖SM4GCM(enc_k,K,SESSION_KEY_AAD))",
        "status": "pending | active | ended",
        "ephSkEnc": "B64(nonce‖SM4GCM(enc_k,eph_sk,EPH_SK_AAD)) 或空串",
        "outSeq": 3,
        "seenSeqs": [1, 2],
        "createdAt": 1794211940,
        "lastCode": "CTK1:…（最近一次邀请码/接受码）"
      }
    ]
  }
}
```

- `ephSkEnc` 只在发起方 `pending` 阶段非空，握手完成即清空；接受方始终为空。
- `seenSeqs` 只保留最近 500 个序号。
- `lastCode` 用于界面重新展示未完成的邀请码/接受码。

### 11.4 `messages.json`

```json
{
  "version": 1,
  "messages": {
    "<contactId>": [
      {
        "id": "UUID",
        "contactId": "…",
        "sid": "9f3a1c02b7d84e65",
        "direction": "incoming | outgoing | system",
        "kind": "text | system",
        "envelope": "CTK1:…",
        "text": "",
        "seq": 1,
        "ts": 1794211940
      }
    ]
  }
}
```

- `kind=text`：`envelope` 为密文，`text` 恒为空；明文仅在解锁期间存在于内存缓存。
- `kind=system`：本地提示（如「已发起新会话」），不含秘密，明文保存在 `text`，`envelope` 为空。
- 删除联系人会同时删除其会话与消息文件中的对应条目。

### 11.5 内存与磁盘对照

| 数据 | 磁盘 | 内存（解锁时） |
|---|---|---|
| 身份私钥 `sk` | 仅 `skEnc`（SM4-GCM） | `identitySk` |
| `enc_k` | 不落盘（由 PIN+unix 重算） | `encKey` |
| 会话密钥 `K` | 仅 `keyEnc`（SM4-GCM） | 会话缓存 `sessionKeyCache` |
| 发起方临时私钥 | 仅 `ephSkEnc`（握手完成前） | 解密后瞬时使用 |
| 聊天明文 | 不落盘 | `messageTextCache`，锁定即清空 |
| 公钥、用户名、联系人 | 明文 | 明文 |

## 12. 会话状态机

每个联系人有独立的会话列表；同一时刻最多一条 `active`、最多一条 `pending`（代码取「最后一条」）。

```
             startSession()                 completeSession()
  (无) ──────────────────► pending ──────────────────────► active
                              │                               │
                              │ startSession()                │ startSession()
                              │（重新发起）                   │（新会话）
                              ▼                               ▼
                            ended ◄────────────────────────── ended
                              ▲
                              │ acceptInvite()（接受对方邀请：对方旧会话被置 ended）
                              │
                           active（responder 直接进入）
```

规则：

- 发起方 `startSession`：把该联系人原有 `active`/`pending` 全部置 `ended`，新建 `pending` 记录并输出邀请码。
- 接受方 `acceptInvite`：验证通过后新建 `active` 记录，原有 `active`/`pending` 置 `ended`。
- 发起方 `completeSession`：当前 `pending` 转 `active`，其余 `active` 置 `ended`。
- `ended` 会话仍保留 `keyEnc` 与 `seenSeqs`，用于解密此前未粘贴的历史消息；但不再用于发送。
- 解锁后 `sessionKeyCache` 清空，按需从 `keyEnc` 解密回填。

## 13. 错误处理与拒绝条件

| 场景 | 检查 | 结果 |
|---|---|---|
| 用户名/名称超长 | > 32 字符 | 拒绝 |
| PIN 格式 | 不匹配 `^[!-~]{6,16}$` | 拒绝 |
| 两次 PIN 不一致 | 字符串比较 | 拒绝 |
| 解锁失败 | GCM 校验失败或公钥不一致 | 「PIN 错误」 |
| 公钥格式错误 | hex 解码/曲线校验失败 | 拒绝添加联系人 |
| 添加自己 | 规范 pk 相同 | 拒绝 |
| 重复联系人 | 规范 pk 相同 | 拒绝 |
| 邀请码公钥不匹配联系人 | 规范字节比较 | 「邀请码不属于当前联系人」 |
| 邀请码用户名不匹配 | `from != contact.name` | 拒绝 |
| 邀请/接受签名伪造 | SM2 验签失败 | 拒绝 |
| 接受码 sid 不匹配 | 重新推导 `sid' != envelope.sid` | 「接受码与当前会话不匹配」 |
| 消息发送者不匹配 | `envelope.pk != contact.pkHex` | 拒绝 |
| 会话不存在 | 按 sid 查不到 | 拒绝 |
| 重复消息 | `seq ∈ seenSeqs` | 「这条消息已经解密过了」 |
| 消息被篡改/AAD 不符 | GCM 标签校验失败 | 拒绝，不落盘 |
| 未建立会话时发送 | 无 `active` | 「请先建立会话」 |
| 锁定状态操作 | `locked=true` | 「应用已锁定」 |

## 14. 安全属性与已知限制

### 14.1 已具备

- 身份私钥、会话密钥、临时私钥在磁盘上均为 SM4-GCM 密文，密钥由 PIN 派生。
- 每条密文使用独立随机 96 位 nonce 与 128 位认证标签，篡改可检测。
- 临时 ECDH + 签名认证，握手具备双向身份认证；每次新会话重新协商密钥。
- 消息 AAD 绑定 `sid`、发送者用户名/公钥、序号，防止字段替换与跨会话重放。
- `seq` 去重 + 公钥/会话匹配，防止简单重放粘贴。
- PIN 错误时通过 GCM 标签 + 公钥重推导双重校验，不泄露「是哪一步失败」的具体细节。

### 14.2 限制（按当前规格实现，未额外加固）

1. **离线暴力破解 PIN**：`enc_k = SM3(pin ‖ unix)` 只做一次 SM3，无 KDF 拉伸（如 PBKDF2/scrypt/Argon2）。攻击者拿到 `profile.json` 后可在本地高速尝试 PIN，6 位 PIN 的搜索空间有限。若需提升，应改为慢速 KDF 并增加版本字段。
2. **无前向保密（存储层面）**：虽然握手用临时 ECDH，但会话密钥 `K` 会以 `enc_k` 加密后长期保存，以便之后解密历史。PIN + 设备文件同时泄露时，历史会话密钥与私钥均可恢复。
3. **信封元数据明文**：`from`、`pk`、`eph`、`sig`、`sid`、`seq` 在信封 JSON 中未加密（仅 Base64 编码）。第三方通道可看到用户名、公钥、会话 ID 与序号，只有正文 `ct` 被加密。
4. **签名上下文有限**：`sig` 只覆盖 65 字节临时公钥，未覆盖 `type`、`sid`、`from`。协议通过「公钥必须等于已保存联系人公钥」及「sid 重新推导比对」来约束，但更稳妥的做法是把协议版本、角色、会话标识一起纳入签名/验签消息。
5. **重放窗口**：`seenSeqs` 仅保留最近 500 条；超出窗口的旧序号理论上可再次被接受（密文相同则明文相同，影响有限）。
6. **无严格顺序与丢失检测**：不校验 `seq` 连续性，粘贴顺序任意；消息丢失只能由用户自行判断。
7. **本地运行环境**：JVM 无法保证密钥材料从内存中安全擦除；明文在界面可见，复制的是密文而非明文。设备被完全控制（root/调试器）时，解锁期间的密钥可被读取。
8. **PIN 共享派生密钥**：所有本地加密对象共用同一个 `enc_k`，依靠随机 nonce 与不同 AAD 做域隔离。
9. **未做密钥轮换/棘轮**：需要新安全性时只能重新发起会话（重新生成临时密钥）。
10. **应用签名**：当前 macOS 安装包未做代码签名/公证，Android 为 debug 签名，不适合直接分发。

## 附录：AAD 与域隔离一览

| 用途 | AAD 常量/格式 | 所在协议 |
|---|---|---|
| 身份私钥加密 | `crypttalk/profile/sk/v1` | P1 / P7 |
| 会话密钥加密 | `crypttalk/session/key/v1` | P4 / P7 |
| 发起方临时私钥加密 | `crypttalk/session/eph-sk/v1` | P4 / P7 |
| 消息加密 | `CTK1\|msg\|<sid>\|<from>\|<pkHex>\|<seq>` | P5 |

所有 AAD 以 UTF-8 参与 GCM 认证；AAD 不匹配时解密必然失败。
